# 話者修正と境界再書き戻し：再現手順と検証記録

2026-09-08。基準は `44176ed`（ユーザー実機確認の記録）。変換実装とPhase 1検証は、その祖先 `cbbc7a4` に含まれる。

## 今回の結果

Premiere Pro 2025 25.6.6、既存45秒サンプル、16区間・118単語・仮2話者で、2番目の区間だけを話者Bから話者Aへ変更した。表示試験用の仮変更であり、音声上の話者を正しく識別した結果ではない。

- 独自masterの1区間だけ話者keyを変更して再変換した。
- 既存の話者UUID・名前、単語本文・開始時刻・duration・その他フィールド、残り15区間の話者割当を保持した。
- 対象固定の公式UXPで再Import、保存、プロジェクトを閉じて再オープンし、期待結果と全フィールドを比較した。数値の許容差は1マイクロ秒。
- 同じ候補を再適用し、再度保存・再オープン後の一致を確認した。16区間・118単語・2話者が保持され、重複はなかった。
- 画面上で対象文が話者A、次の文が話者Bであることを確認した。
- 映像・音声トラックのクリップ範囲とシーケンス終端が、前回成功時の保存後記録と一致した。
- 失敗した途中試験ではバックアップTranscriptの再適用・読み戻し一致・保存を確認した。最終成功処理後の復旧試験、Undo/Redo、境界分割・結合は未実施。
- 変更前の検証プロジェクトと45秒MOVは前後SHA-256が一致した。外付けSSDの元素材は本試験では使用・再ハッシュしていない。

## 判明した実行条件

`importFromJSON` をロック外で実行した試験ではTransactionはtrueだったが、直後と保存・再オープン後の `exportToJSON` が `Illegal Parameter type` を返した。区間長の保持方法とUUIDの新規生成を変えても改善しなかった。

成功時の処理に合わせ、**TextSegments生成、Action生成、Transaction実行を同じ `lockedAccess` 内へ揃えた試験が成功**した。根本原因や他バージョンへの一般性までは確定していない。JSON文字列化・入力検証・対象照合・ファイル操作はロック外で行い、ロック内に非同期処理を入れない。

再利用する処理は `../uxp/import-transcript.js`。これは低水準のImport処理だけであり、対象照合・バックアップ・復旧・保存を自動で担う汎用インポーターではない。Transaction成功だけを反映確認と扱わない。

回帰検査は既存Pythonテスト4件と `tests/test_import_transcript.js` を実行して成功した。後者はロック内生成、毎回の新規生成、Transaction拒否、Undoラベル必須を確認する模擬ホストの検査であり、実機検証の代用ではない。

[Adobe Transcript API](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/transcript) と [Project API](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/project) の25.6対応定義を参照した。26系実機は今回未検証。

## 入出力の差

Premiereの読み戻しJSONは、単語時刻を保持したままsegment.durationを無音区間側へ伸ばす場合がある。独自masterからの出力JSONとの完全な数値一致を期待しない。

今回の候補入力は成功エクスポーターの区間長を使用し、期待する読み戻し値は事前exportの区間長とした。新規生成UUIDは、独自masterの話者keyと既存表示名の対応を確認して既存UUIDに対応付けた。話者名だけによる自動推定は行わない。この対応付けと区間長の扱いを、任意素材向けの汎用仕様として確定したものではない。

## 再現手順

1. 正本の基準コミット、Premiereバージョン、対象素材を確認する。今回の成功入力master・生成JSON・読み戻しJSONを固定して保管する。
2. 対象を読み取り専用でexportし、プロジェクトパス/GUID、素材名、メディアパス、Transcriptをローカル保存する。対象名が複数ある場合は停止する。
3. プロジェクトファイルのバックアップを作成し、PremiereのsaveAsで検証コピーを作る。アクティブProjectを再取得し、コピーのパスを再照合する。
4. 独自masterの1区間だけ話者keyを変更する。元masterを上書きせず、成功エクスポーターで別ファイルへ変換する。
5. 話者keyと既存UUIDの対応を固定し、期待される差分が1区間のspeakerだけであることを検査する。本文・単語時刻・未修正区間の差異があればImportしない。
6. 書き込み直前に対象を再照合し、現在のTranscriptがバックアップと一致することを確認する。上記Import処理を実行する。
7. 検証コピーを保存・再オープンし、対象を再取得してexportする。読み戻しは期待JSONの全フィールドを比較する。
8. 同じ候補を再適用し、保存・再オープン後に比較する。画面で変更箇所と隣接区間を確認する。
9. 不一致・エラー時は対象を再照合してバックアップをImportし、読み戻しと保存結果を記録する。復旧失敗時は成功扱いにせず、バックアップのプロジェクトファイルを復旧元として残す。

実データ、対象パス、UUID、プロジェクト、プラグイン内に埋め込んだTranscript、ログはローカルだけに保持する。Gitへ登録しない。

## 境界分割・結合・再適用の結果

同じ45秒素材の別プロジェクトコピーで、元の16区間・118単語・2話者のうち、10.40秒から13.52秒の一区間を単語境界12.22秒で分割した。先頭6単語を話者A、残り11単語を話者Bに割り当て、17区間・118単語・2話者の候補を公式UXPでImportした。

- 保存、プロジェクト再オープン、全フィールド比較、同一候補の反復適用まで成功した。
- 読み戻しは17区間・2話者で、対象プロジェクトパス、素材名、メディアパスを照合した上で記録した。
- 結合候補（16区間）への戻しも検証コピーで実行され、読み出しで16区間になったことを確認した。
- 中断・クラッシュ後に検証コピーを開き、保存されていた17区間・118単語が期待JSONと全フィールド一致することを確認した。
- その後、17区間→16区間の結合候補→17区間の分割候補を実行。それぞれ保存と全フィールドの読み戻し比較に成功した。
- プラグイン処理の完了後、Premiereのメニューで検証コピーを閉じ、別操作で再オープンした。再exportした全フィールドは17区間・118単語の期待JSONと1マイクロ秒以内で一致した。
- この試験は既存の候補JSONとバックアップJSONの再Importを確認したもの。汎用ヘルパーを直接呼び出す実機統合、境界付近の画面表示、今回のタイムライン範囲比較は未確認。

### クラッシュ後の再開手順

クラッシュ直前の処理完了は推定せず、最初に読取専用exportを行う。今回、再起動後の日本語パスは分解形で返され、文字列の直接比較では対象不一致となった。プロジェクトとメディアの両パスをNFCに正規化して完全一致で照合した。名称の部分一致やGUIDだけの照合へは緩めない。

同一プラグイン処理内でのclose/openは再開試験では使用せず、Import・比較・保存の処理が終了した後に、UIで閉じて別操作で開いた。この変更で今回の確認は完了したが、先のクラッシュ原因を特定したものではない。生ログはローカルの `recovery-inspect.log`、`recovery-merge.log`、`recovery-reopened.log` に保持する。

`uxp/transcript-boundaries.js` はこの検証で用いた、Premiere APIを呼ばない純粋なJSON操作を提供する。`splitSegmentAtWord` は単語境界で分割し、元の区間の開始・終端と単語順を保つ。`mergeSegments` は隣接して連続する二つの区間だけを、明示された話者で一つに戻す。これらは対象照合、バックアップ、Import、保存、読み戻し比較を代替しない。

## 次の検証

### 日本語素材での追加確認（2026-09-08）

再利用ヘルパー `mergeSegments` と `splitSegmentAtWord` を試験プラグイン内から実際に呼び出し、読取済み17区間から結合16区間・再分割17区間の候補を生成した。既知の期待JSONとの一致を確認してからImportし、各段階の保存と全フィールド比較に成功した。入力バックアップはローカル `integration-before.backup.json`、結果は `integration-result.log` に保持する。

続けてPremiereの編集メニューで取り消しを実行し、16区間の読み戻しが結合時の期待JSONと一致した。やり直しで17区間へ戻し、保存操作後に再exportして分割時の期待JSONと一致することを確認した。比較許容差は1マイクロ秒。記録は `undo-result.log` と `redo-result.log`。この追加試験ではプロジェクトの再オープンは行っていない。

文字起こしパネル内のスクロール・座標クリックは操作エラーとなったため、公式UXP `SourceMonitor.play` と `getPosition` でソースを再生・停止し、文字起こしパネルを追従させた。12.3123秒と10.7440667秒で停止した画面を確認し、次の表示を目視確認した。

- 話者A（仮）: `00;00;10;11 - 00;00;12;06`、本文「これ、普段オリジ」
- 話者B（仮）: `00;00;12;06 - 00;00;13;15`、本文「ナルメニューとしてはなくて、」

12.22秒の分割境界に対応する画面時刻で話者が切り替わっている。この分割は日本語の単語断片の途中に設定した表示試験用の仮変更であり、音声上の話者識別精度は評価していない。再生位置の変更のみで、Transcriptやタイムラインの編集は行っていない。

- 上記により、ヘルパーからの実機統合、Undo/Redo、境界付近の画面表示の追加確認は完了した。
- 対象変更・失敗時復旧の追加確認は下記参照。今回確認した復旧・Undo/Redoは上記45秒素材の分割・結合操作に限定する。
- 日英混在サンプル、言語切替位置、話者割当の評価基準を揃える。話者と言語を同一視しない。
- 翻訳字幕は原文・話者・時刻の経路が安定した後の別工程とする。

## 対象不一致と保存失敗時の復旧試験（2026-09-08）

検証コピーの17区間を新たにexportし、ローカル `safety-before.backup.json` に保存した。対象固定の試験用プラグインで、期待するプロジェクトパス・クリップ名・メディアパスを一つずつ意図的に不一致にした。3ケースとも対象解決で停止し、正常な対象へ戻して再exportした全項目はバックアップと一致した。実際の別プロジェクトへ切り替えた試験や、照合後に対象が変更される競合の試験ではない。

次に同じコピーへ16区間の結合候補をImportし、読み戻し一致を確認した。保存成功値をfalseにする障害注入でエラー処理へ進み、17区間のバックアップを公式UXPで再Importして復旧した。復旧後の全項目一致と実際の `project.save()` の成功を確認した。結果はローカル `safety-result.log` に記録した。

保存失敗は試験コード内の模擬応答であり、Premiereの実際の保存APIを失敗させたものではない。ディスク容量不足・権限変更などの実I/O障害、汎用インポーターの障害処理、製品画面の「反映済み」表示は未検証。この結果から製品全体の保存失敗対応を完了とはしない。復旧後の追加再オープンも今回は実施していない。
