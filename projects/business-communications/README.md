# 業務連絡管理システム

## 開発仕様 1.0

受信、保存、宛先解決、判断、送信を独立させる。既存の案件管理と動画納品の稼働を維持する。公式LINEの実機試験は独立したテスト用アカウント・保存先・資格情報を使う。費用追加、本番移行、取引先への実送信は本人確認後に進める。

### 受信と共通台帳

HTTPS中継で未加工の本文と X-Line-Signature を使って HMAC-SHA256 を照合する。確認用の空のイベント配列には 200 を返す。保存ワーカーへの転送も認証する。署名未検証の試作は合成データを使う隔離テストに限定する。

LINEイベントは内容で選別せず、イベントIDで重複排除する。受信ID、経路、環境、受信・記録日時、送信者IDと表示名、会話ID、イベントID、メッセージID、種別、本文、元ファイル名、Drive IDとURL、保存状態、案件処理状態、案件ID、移動先ID、エラー、試行回数を保持する。送信者ID欠落時は空欄とし会話IDで代用しない。テキスト台帳と原文を関連付ける。既存月別ログは保全し、新規環境での月別原文の保存方法を切り分ける。添付はMessaging APIから速やかに取得し、非公開のDrive年月フォルダに保存する。同名上書きを禁止し、取得失敗と受信済みを区別する。後からDrive IDで追跡できるようにする。受信から案件作成・移動・送信を起動しない。

### 送信

Python、GAS、エージェントは共通の認証付きPOSTまたは台帳キューから送信指示を登録する。GET起動とBroadcastは採用しない。宛先、環境、依頼元、送信内容、ファイル、承認、予約・条件、冪等性キーを記録し、送信IDで照会できるようにする。キュー登録と獲得は単一ワーカーとスクリプトロックで排他する。リースと試行履歴を保存する。Pushは送信IDに固定したリトライキーを使用し、応答不明は結果不明として扱う。承認後に宛先・本文・添付が変われば再確認する。テストでは本人確認済みのユーザーIDだけを許可する。返信失敗でPushに切り替えない。API受付と相手の受信は区別する。

テキストとURLを優先する。直接送信可能なメディアは公式APIの制限と安全な公開方法を確認する。PDF、Office文書、ZIPは権限確認済みの共有URLを使用する。月間利用量を取得し、枠接近を本人へ通知する。プラン変更や追加課金は行わない。納品本文は「拡張子付きファイル名 半角スペース 分'秒\"」とURLの2行。尺は最も近い秒に丸める案とし境界は検証対象。4本以上は確定済みのまとめURLを使用し、送信直前に受取人のアクセス権を確認する。共有単位は本人の個別指示を優先する。

### 連絡先

Googleコンタクトを人物情報のマスター、Notionを案件・発注・請求関係の管理、台帳を内部IDとLINE識別子の対応先とする。人物、所属、発注元、請求先を分離する。LINE対応は環境とチャネル単位で保持し、取得元と確認状態・履歴を記録する。同姓同名・改名・未確認・失効を識別し、表示名一致だけで確定しない。グループを個人と区別する。候補提示後に本人が既存連絡先との紐付けを確認する。既存連絡先の作成・上書きは初期対象外。

### 判断と実行

共通タスクとバージョン付き判断JSONを持ち、入力、根拠、分類、実在候補、操作案、不確定情報を区別する。ルールと手動判断を先に用意し、AI提供元は交換可能とする。エージェントは個別認証・読取と提案に限定。モデルには許可済みデータだけを渡す。未知の型・操作・架空ID・競合は明示的に拒否または保留する。受信本文・添付の命令は業務データとして扱う。

日程はカレンダー単位、発注・請求は案件単位。同じ番組名だけでは案件や発注元を統合しない。別名、担当、編集期間、発注単位、確認済み案件IDを照合する。資料だけの受信で新規案件を作らず、標準の子フォルダを案件扱いしない。移動先、親案件、共有権限を確認し、IDと移動履歴を保持する。実行は原則ドライランから開始し、承認、期待バージョン、操作単位の冪等性、部分失敗時の再開を備える。既存カレンダー・Notion同期との重複が解消するまで書き込まない。

### 順序と合格条件

1. LINE受信。署名拒否、空イベント、テキスト、画像・PDF、同名ファイル、再配信、途中失敗、再試行、再起動、未知のイベント、既存環境への副作用を検証。
2. 台帳拡張・連絡先・送信。本人宛テキスト／リンク、未確認宛先、予約、変更時の再承認、並行獲得、通信不明、再起動、共有権限不足を検証。
3. 本人が選別したスクショ取り込み、案件と日程の判定、資料振り分け。匿名化した合成・承認済みサンプルとドライランで誤登録、保留、処理時間を測る。
4. Gmail・SMSは業務候補だけを抽出し、後段に渡す。実機接続、判断精度、運用条件は検証後に確定する。

### 既存資産と移行

受信GAS控えの月別テキスト保存は原文保全の要件に反映する。既存コードは月別ファイルの読み戻し・再書き込み方式で、署名検証とイベント重複排除がないため、新規受信の入口には使わない。送信GAS控えのGET起動とBroadcastは採用しない。控えと既存保存領域は保全する。案件管理GASの15分間隔トリガーを確認済み。新基盤との統合には並行ドライラン、重複防止、復旧手順が必要。

運用情報、レビュー原文、取引先例、非公開の参照先は非公開仕様書で管理する。ホスティング、保持期間、大容量添付、接続権限、実際の料金・制限は各段階で公式仕様と実機を確認する。
