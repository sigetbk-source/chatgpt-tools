# 開発ルール

## 1. 開発の正本

コード、仕様、設計判断、手順、変更履歴はこの GitHub リポジトリで管理する。チャットや外部ノートだけに重要な決定を残さない。

## 2. ブランチと変更単位

- 原則として機能・修正ごとにブランチを作る。
- コミットは目的が一つになる大きさにする。
- 仕様変更と関連文書の更新を同じ Pull Request に含める。
- `main` は動作確認済みの状態を維持する。

## 3. 設計原則

- SwiftUI を UI の標準とする。
- Apple 純正フレームワークを優先し、MVP では不要な外部依存を追加しない。
- 発売日時は絶対時刻として保存し、表示時に端末のタイムゾーンへ変換する。
- 通知は `UNUserNotificationCenter`、URL 起動は SwiftUI の `openURL` を基本とする。
- アプリがバックグラウンド中に Safari を自動起動できるとは扱わない。
- 保存形式には将来の移行を考慮した安定した識別子を持たせる。

## 4. テスト

最低限、次を確認する。

- 入力検証: 空の名前、不正 URL、過去日時
- カウントダウン: 60 秒境界、0 秒、時刻経過後
- 通知: 権限許可・拒否、再登録、編集、削除
- URL 起動: 前面時の自動起動、通知タップからの起動
- 永続化: 再起動後の復元、編集・削除
- 実機: 通知音、ロック画面、バックグラウンド復帰

時刻依存ロジックは現在時刻を注入できる設計にし、待ち時間なしで単体テストする。

## 5. レビューと完了判定

複雑な変更（複数領域への影響、通知やライフサイクル、永続化、技術的不確実性、回帰リスクが高い変更）は、実装担当とは別の担当がレビューする。

完了条件は、要求仕様を満たし、重大な回帰がなく、関連テストが通り、文書が同期していること。Xcode 未導入や実機未確認の段階では「実装完了」としない。

## 6. 履歴

- 開発上の判断と検証結果は `docs/development-log.md` に追記する。
- 利用者に見える変更は `CHANGELOG.md` の `Unreleased` に追記する。
- リリース時にバージョンと日付を確定する。
