# GitHub 運用ルール

## 目的

GitHub 上のコード、設定、スキル定義、固定資産、関連 Markdown を開発の正本として保ち、AI がリポジトリを読めば構造・運用・検証状態を判断できるようにする。

## リポジトリの基本方針

- 新しい分野や小規模ツールは、原則として `chatgpt-tools` に集約する。新規リポジトリはむやみに作らない。
- 再利用可能な ChatGPT / AI ワークフローやスキルは `skills/<name>/` に置く。
- 独立したアプリや実装プロジェクトは `projects/<name>/` に置く。
- リポジトリ全体に共通する運用ルールや設計方針は `docs/` に置く。

## 新規リポジトリを検討する条件

次のような明確な分離理由がある場合だけ、新規リポジトリを検討する。

- ユーザーが独立リポジトリを明示的に希望している
- 公開範囲またはアクセス権限を分ける必要がある
- 独立した CI/CD、デプロイ、リリース管理が必要である
- 大きな履歴、Issue、Pull Request、バージョン体系を分離する必要がある
- ライセンス、所有権、依存関係などの制約が異なる

新規リポジトリが必要でも、現在の GitHub コネクタではリポジトリ作成操作を利用できないことがある。その場合は、ユーザーが GitHub UI で空のリポジトリを作成し、接続確認後に AI が中身を投入する。

## 既存リポジトリの集約

- 移行前に、移行元の既定ブランチ、現行ファイル一覧、最新コミット、公開範囲、アーカイブ状態を確認する。
- まずは現行内容を `projects/<name>/` または `skills/<name>/` へコピーし、集約先で確認できる状態にする。
- 履歴を完全移植できない場合は、現行ファイル一式を優先し、移行元リポジトリ、参照ブランチ、参照コミット、コピー日、履歴移植の有無を README に明記する。
- 元リポジトリを AI の判断だけで削除・アーカイブ・破壊しない。集約先の内容を確認した後、元リポジトリをどう整理するかはユーザーが判断する。
- 移行中も秘密情報、署名データ、個人情報、ローカル専用設定を取り込まない。

## 管理対象と除外対象

GitHub で管理するもの:

- ソースコード
- 設定ファイル
- スキル定義
- 実行に必要な固定資産
- 仕様、設計、運用、検証結果、変更履歴
- 意図を示すために必要な完成サンプル（例外として README 等に用途を明記する）

原則としてコミットしないもの:

- ビルド生成物
- キャッシュ
- 一時ファイル
- ローカル作業用ファイル
- 自動生成できる中間成果物
- パスワード、トークン、証明書、署名データ、個人情報

各プロジェクトやスキルの `.gitignore` と README で、必要に応じて具体的な除外規則を補足する。

## ドキュメントと変更管理

- ルートの `README.md`、`AGENTS.md`、`docs/`、各プロジェクトやスキルの README / AGENTS.md を、AI が読めば構造と運用が分かる状態に保つ。
- 作業前にルート文書と対象ディレクトリの文書を読む。
- 重要な仕様変更では、コードだけでなく関連する README、仕様書、設計文書、開発ログ、CHANGELOG も同じ変更単位で更新する。
- 実装済み、テスト済み、実機確認済み、提案中を区別し、未検証事項を完了として記載しない。
- 複雑な変更は独立レビューを行い、指摘を修正して再確認する。
